# W2 设计笔记：详情页数据怎么拿（2026-10-24 现场提问整理）

> 起因：写完 `parse_cards` 后问「这 8 行怎么拿到详情页的参数？」
> 结论：拿不到，也不该由它拿。列表页和详情页是两套标签结构，必须两个解析入口。

## 1. 实测：两套结构完全不同

**列表页** `index.html`（`parse_cards` 负责）

```html
<article class="card" data-sku="K87">
  <h2 class="name">机械键盘 K87 青轴</h2>
  <p class="price">¥499<small>¥599</small></p>
  <a class="detail-link" href="detail/p1.html">查看详情</a>
</article>
```

**详情页** `detail/p1.html`（`parse_cards` 在它上面返回 **0 条**）

```html
<h1 class="name">机械键盘 K87 青轴</h1>
<p class="price">¥499</p>
<table class="spec">
  <tr><th>轴体</th><td>青轴（段落感强，声音清脆）</td></tr>
  ...
</table>
```

实测抽取结果（2026-10-24，mock 站 p1）：

```
参数对 6 组：{商品编号: K87, 轴体: 青轴（段落感强，声音清脆）,
             键位数: 87 键, 接口: Type-C 可拆线, 重量: 780 g, 库存: 32}
标题 = 机械键盘 K87 青轴    价格 = 499
```

## 2. 两种设计，选 B

| | A. 每站一个函数 | **B. 通用 `parse_by_selector(html, field_map)`** |
|---|---|---|
| 写法 | `parse_mockshop_list` / `parse_mockshop_detail` / ... | 一个函数 + 一份配置 |
| 换站点 | 改代码 | 只改 `targets.field_map`（数据库里的配置） |
| Agent 能做决策 | 不能（函数名写死了站点） | 能（选哪个 field_map 由它挑） |

`field_map` 形态（对应审查报告 P0-3）：

```json
{"sku":   {"sel": "article.card",      "attr": "data-sku"},
 "name":  {"sel": "h2.name",           "attr": null},
 "price": {"sel": "p.price",           "attr": null, "cast": "money"},
 "url":   {"sel": "a.detail-link",     "attr": "href", "join": "base"}}
```

两个必须记住的点：
- **`attr: null` 表示取标签文本，非 null 取属性值** —— `url` 要的是 `href` 属性，不是「查看详情」这四个字。审查报告 P0-3 说的就是这四种字段四种取法。
- **`join: base` 必须走 `urljoin`** —— 字符串拼接在 base 带尾斜杠时恰好对、不带就 404。

## 3. 详情页参数表是「动态键」，`field_map` 装不下

`<th>轴体</th><td>青轴…</td>` 里，**键名本身就是数据**（这个商品可能是轴体，那个可能是 DPI）。固定字段列表无法穷举。

→ 单独一个 `parse_kv_table(html)`：抓全部 `th/td` 对成 dict，整个 JSON 塞进 **`records.extra`**（建表时已预留 Text 字段）。

## 4. Agent 何时才抓详情页（面试口径）

- 「这些配件里哪个最贵」→ 列表页 1 次请求足够，**不该抓详情**
- 「键盘是什么轴体」→ 才追加 `detail/pN.html`

> 工具只有 `fetch_page` / `parse_by_selector` / `save_records` 三个原子能力，抓几层、抓哪个 URL 由模型决定。
> 若拆成 `fetch_list` + `fetch_detail`，模型就没得选，退回固定两层脚本。
