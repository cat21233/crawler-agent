# 采集结果存储设计：A / B / C 三方案取舍

> 状态：**决策已定 —— 按 A 走（MVP 前不动表结构）**　日期：2026-11-18
> 起因：讨论中提出「每一个任务爬取的数据应该放在不同的表里面」。这不是一句随口的话，
> 它对应三种完全不同的工程代价。本文把三条路的成本写清楚，并把「现在为什么选 A」落到证据上，
> 避免后面接手的人（或三个月后的自己）重复讨论一遍。

---

## 1. 结论先行

| 问题 | 答案 |
| --- | --- |
| MVP（11-26）用什么 | **A：单表 `records` + `extra` JSON 文本列**（= 现在的实现，零改动） |
| 为什么不按站点分表 | 分表把「加一个站点」从**改配置**变成**改代码 + 迁移**，而且毁掉通用查询与通用前端渲染 |
| 什么时候必须升级 | 出现「跨站点按业务字段筛选/聚合」「单站点 > 百万行且字段 < 10 个」两类需求之一 → 升 **B** |
| C 还用不用得上 | 只在「客户要求物理隔离 / 每站点字段数 > 30 且强类型」时才值得，MVP 与实习面试都不需要 |

## 2. 三种方案分别是什么

### A. 单表 + extra（现状）

```sql
-- records 表（db_models.py:80）
id, target_id, title, price, url, url_hash, extra TEXT, crawled_at
UNIQUE(target_id, url_hash)      -- 幂等去重
```

- 固定 4 个通用维度：`title / price / url / crawled_at`（所有站点都有）
- **表里没有独立列的字段，全部 JSON 序列化进 `extra`**（`agent/tools.py:140` 的 `extra_fields`）
- 例：豆瓣电影 → `{"info":"1994 / 美国 / 剧情","rating":"9.7","votes":"280万"}` 全在 `extra` 里

### B. 单表 + 真 JSON 列 + 生成列索引

```sql
extra JSON,                                    -- Text → JSON，可用 JSON_EXTRACT
rating VARCHAR(20) AS (extra->>'$.rating') STORED,   -- 生成列，可建索引
INDEX ix_rating (rating)
```

- 表还是那**一张**，加站点仍然只改配置
- 但「按 rating > 9 筛选」从「读出来 Python 过滤」变成「走索引的 SQL」
- 代价：要先知道「哪些字段值得升成列」→ 需要新站点上线后观察，属于**有数据才能做的优化**

### C. 一站点一表（物理分表 / 动态 DDL）

```
records_douban_chart / records_mock_list / records_xxx ...
```

- 每种页面结构建一张物理表，字段强类型、全部可索引
- 加一个站点 = 建表（`CREATE TABLE` 写进 pipeline，或按 `schema_json` 物化）
- 代价：迁移、通用查询、通用前端渲染、备份、统计全部要按「N 张表」重写一遍

## 3. 对比表

| 维度 | A 单表 + extra | B 单表 + JSON 索引 | C 一站点一表 |
| --- | --- | --- | --- |
| 现在改造成本 | **0**（已在跑） | 半天~1 天 | 2~3 天 |
| 加一个站点 | 改 `field_map` 配置（0 行代码） | 改配置（0 行代码） | **建表 + 改 pipeline + 迁移脚本** |
| 字段强类型 | ❌ 全是字符串 | 🟡 常用字段可强类型 | ✅ 全强类型 |
| 按业务字段筛选 | ❌ 拉回内存过滤 | ✅ `JSON_EXTRACT` / 生成列索引 | ✅ 原生 WHERE 走索引 |
| 通用查询接口 | ✅ 一条 `SELECT` | ✅ 一条 `SELECT` | ❌ 要 UNION N 张表，或维护路由表 |
| 通用前端渲染 | ✅ 一套表格 + `extra` 折叠展示 | ✅ 同上 | ❌ 每个站点写一套列定义 |
| 跨站点统计 | ✅ `GROUP BY target_id` | ✅ 同左 | ❌ 先 UNION 再统计 |
| 空字段浪费 | ✅ 无（JSON 里没有就没有） | ✅ 无 | ❌ 电影表永远空着 price |
| 表数量 | 1 | 1 | N（且随站点线性增长） |
| 面试可讲性 | 「我知道它弱在哪，也知道什么时候该换」 | 同左 + 具体优化 | 「我按站点建了 20 张表」→ 追问就露 |

## 4. 为什么 MVP 前选 A（五条理由，按重要性排）

1. **A 的弱点在 MVP 验收条件里根本不出现。**
   MVP 七条要求的是「一条指令 → 抓取 → 入库 → 可观测 → 前端可见」。
   没有任何一条要求「按 rating 做 SQL 筛选」。为不存在的需求付 2~3 天，是拿验收时间换想象中的优雅。

2. **分表直接摧毁「配置驱动」这个项目最核心的卖点。**
   现在加一个站点 = 新建一条 `targets` 记录（`url` + `field_map`），**一行业务代码都不改**。
   分表之后，新站点的字段组合一旦没出现过，就必须 `CREATE TABLE` ——
   Agent 的「自主」就退化成「人先给它建好表」，这跟项目定位冲突。

3. **`records` 只存 4 个固定维度是**有意的**，不是偷懒。**
   抓下来的东西结构差异极大（商品有 sku、电影有导演、文章有作者），
   但它们**同构的部分**恰好是「叫什么、多少钱、在哪、什么时候抓的」。
   把这 4 个维度抽出来做列、其余塞 `extra`，是「稳定骨架 + 弹性血肉」的经典取舍。

4. **分表会让剩下的 W4 工作量直接翻倍。**
   W4 前端现在是「一套通用表格」，字段从 `/records` 拿固定 4 列 + `extra` 展开。
   分表后要么写 N 套列定义，要么写一套「按 target 动态查表结构」的元编程 —— 后者比 B 方案贵十倍。

5. **B 是 A 的超集，且升级路径是无损的。**
   A → B 只需要一次 `ALTER TABLE`（`extra` 改成 JSON 列）+ 加几个生成列，
   历史数据不用动（`Text` 里的 JSON 串本来就合法）。**现在选 A 不会锁死未来；选 C 会。**

## 5. A 的已知限制 —— 诚实版（每条都给绕过办法）

| 限制 | 现象 | 现在的绕过 |
| --- | --- | --- |
| `extra` 不可索引 | 想「rating > 9」只能全表拉回来在 Python 里过滤 | MVP 数据量小（几百行），全表扫无感；量大就升 B |
| `extra` 是字符串不是 JSON | 前端拿到的是 `"{\"rating\":\"9.7\"}"`，需要 `JSON.parse` | `/records` 接口里 `json.loads` 后按 dict 返回，前端不用管 |
| 字段名没有约束 | 今天叫 `rating`、明天叫 `score`，历史数据两种并存 | `field_map` 由 `_check_field_map` 校验必填键，字段名从配置来，不靠模型即兴发挥 |
| 数值排序按字符串 | `"9.7"` vs `"10"` 排序会错（`"10" < "9.7"`） | 已知坑，前端列表暂不提供排序；升 B 时顺手把 `rating` 生成列设成 `DECIMAL` |

最后一条要特别记住：**这是 A 方案唯一会造成「看起来对、实际错」的地方**，
一旦前端加排序功能，必须先把对应字段升成生成列，不能直接在 `extra` 上排。

## 6. 演进触发条件（写死，避免以后凭感觉拍）

升 **B**（半天~1 天，`ALTER TABLE` + 2~3 个生成列 + 索引）：

- 出现「**跨站点**按同一业务字段筛选或聚合」的需求，且数据量 > 10 万行；
- 或者前端要做「价格/评分排序」——即第 5 节最后一条从「已知坑」变成「用户可见 bug」。

升 **C**（2~3 天）：

- 客户合同里写明「不同来源数据不得同表存放」（合规隔离要求）；
- 或者单站点字段数稳定 > 30 且每个都需要强类型 + 独立索引；
- 或者单表 > 5000 万行、需要按站点分库分表。

**三种情况在实习面试项目里都不会出现**，所以 C 只作为「知道有这条路」记录在案。

## 7. A → B 的具体迁移（真要做时照着走）

```sql
-- ① 先备份（records 是唯一有价值的数据，别省这一步）
mysqldump -u root -p crawler_agent records > records_backup_2026xxxx.sql

-- ② Text → JSON。存量数据是合法 JSON 串，能直接转（若不是，先跑一遍校验）
ALTER TABLE records MODIFY extra JSON NULL;

-- ③ 加生成列 + 索引（字段名取出现频率最高的那几个）
ALTER TABLE records
  ADD COLUMN rating DECIMAL(3,1) AS (extra->>'$.rating') STORED,
  ADD INDEX ix_rating (rating);
```

代码侧只需改两处：`db_models.py` 的 `extra` 类型、`tools.py` 里 `json.dumps` 改成直接传 dict。
`save_records` 的幂等逻辑、`field_map` 驱动的采集逻辑**一行都不用动** —— 这正是 A 的可贵之处。

> 注：生成列与 `->>` 语法需要 MySQL 5.7+；函数索引需要 8.0.13+。
> 当前开发环境为 phpStudy 面板启动的 MySQL，**具体版本未现场确认**，动手前先 `SELECT VERSION();`。

## 8. 面试怎么讲这段（比方案本身值钱）

不讲「我用了单表加 JSON」，讲**取舍链**：

> 「采集结果的 schema 是随站点变的，我先把所有站点共同拥有的 4 个维度抽成列
> （标题、价格、URL、抓取时间），剩下全部塞 JSON 列。这样加一个新站点只改配置不改代码。
> 我知道它的代价 —— JSON 列不可索引、数值只能按字符串排。
> 所以我提前写好了升级路径：常用的业务字段用 MySQL 生成列升成强类型 + 建索引，
> 表结构不用动。真正需要一站点一表的场景是合规隔离或单站点字段超过 30 个，
> 那才值得付动态 DDL 的代价。」

这段话能过三层追问（为什么不拆表 / 怎么查 / 什么时候拆），比「我建了 20 张表」安全得多。
